# Pod Security Standard (PSS)
Pod Security Standards (PSS) define a **built-in**, cluster-wide security baseline for Kubernetes Pods by restricting unsafe behaviors at the Pod and container level. They are designed to replace the deprecated PodSecurityPolicy (PSP) with a simpler, policy-driven, namespace-based model that is enforced by the Kubernetes API server. Pod Security Standards focus on *how containers run rather than who can run them*, making them complementary to RBAC.

## Security Levels
Kubernetes defines three security levels:

### Privileged
The Privileged level is the most permissive and allows Pods to run with essentially no restrictions. Containers can run as root, use host networking, mount host paths, use privileged mode, and access kernel capabilities. This level exists primarily for **system-level components** such as CNI plugins, CSI drivers, and kube-proxy that require deep access to the host. It should never be used for general application workloads.

### Baseline
The Baseline level is a **safe default** that blocks the most dangerous behaviors while remaining compatible with most applications. It prevents privilege escalation, disallows host namespaces (hostPID, hostIPC, hostNetwork), blocks privileged containers, and restricts unsafe volume types like hostPath. However, containers may still run as root and do not require strict security contexts. Baseline is suitable for most workloads that have not been explicitly hardened.

### Restricted
The Restricted level is the **most secure** and enforces strong isolation. Containers must run as non-root, privilege escalation is disabled, all Linux capabilities are dropped, seccomp profiles are required, and only safe volume types are allowed. This level aligns with Kubernetes security best practices and is ideal for production workloads handling sensitive data. Some applications may require changes to comply with this level.

## How Pod Security Standards Are Enforced
Pod Security Standards are enforced using the **Pod Security Admission Controller**, which operates at the namespace level using labels:
- pod-security.kubernetes.io/enforce
- pod-security.kubernetes.io/audit
- pod-security.kubernetes.io/warn

This allows you to enforce, log, or warn about violations independently, enabling gradual adoption without breaking workloads.

Example: ```pod-security.kubernetes.io/enforce: restricted```

### Available Modes
Kubernetes Pod Security Standards (PSS) support three operational modes that control how strictly the policy is applied to Pods within a namespace. These modes let you balance security with adoption velocity by separating enforcement from visibility.

#### Enforce
Enforce is the **strictest mode** and actively blocks Pods that violate the selected Pod Security Standard (Privileged, Baseline, or Restricted). If a Pod does not comply, the Kubernetes API server rejects the request and **the Pod is never created**. This mode is used when you want hard security guarantees, typically in production namespaces, and ensures that no workload can bypass the defined security posture.

#### Audit
Audit *does not block Pod creation but records policy violations* in the Kubernetes **audit logs**. This mode is ideal for security teams and platform engineers who want cluster-wide visibility into non-compliant workloads without impacting running systems. Audit is commonly used to assess existing workloads before switching to Enforce.

#### Warn
Warn *allows Pods to be created but returns a warning message* to the user when the Pod violates the policy. This provides immediate feedback to developers during deployment while avoiding outages. Warn is especially useful in development and staging environments to educate teams and encourage secure-by-default manifests.

#### Why These Modes Matter
These three modes enable progressive security rollout: you can start with **warn** to inform developers, use **audit** to measure impact and track violations, and finally move to **enforce** once workloads are compliant. This staged approach avoids breaking applications while steadily raising the security bar across the cluster.

In practice, mature clusters often run **enforce=restricted** in production, **warn=restricted** in staging, and **audit=restricted** globally to maintain visibility and control.

## Why Pod Security Standards Matter
Pod Security Standards provide a consistent, auditable, and maintainable security baseline across clusters without complex policies. They reduce attack surface, prevent container breakout risks, and make security posture predictable. Combined with **RBAC (who can act)**, **Network Policies (who can talk)**, and **Secrets management (what data is exposed)**, PSS completes the runtime security layer of Kubernetes.

In short, Pod Security Standards define how safe your Pods are allowed to be, by default and by design.


## Example
### Creating namespaces
```
kubectl apply -f ns-baseline.yaml -f ns-privileged.yaml 
```
This step creates two namespaces (baseline and privileged) each labeled with different Pod Security Standards. The privileged namespace allows highly permissive workloads, while the baseline namespace enforces safer defaults. Namespace-level labels are how Pod Security Standards are applied in modern Kubernetes, making security enforcement consistent for all Pods created inside that namespace.

### Creating an nginx pod in the privileged namespace
```
kubectl apply -f pod-privileged.yaml -n privileged
```
Output:
```
Warning: would violate PodSecurity "baseline:latest": privileged (container "nginx-container" must not set securityContext.privileged=true)
pod/pod-nginx-privileged created
```
When you deploy the privileged nginx Pod into the privileged namespace, Kubernetes allows the Pod to be created even though it uses ***securityContext.privileged=true***. The warning appears because the Pod violates the baseline standard, but since the namespace is configured to allow privileged workloads, Kubernetes only warns and does not block creation. This demonstrates that **warn** mode informs users without enforcing restrictions.

### Attempting to create the same pod in the baseline namespace
```
kubectl apply -f pod-privileged.yaml -n baseline
```
Output:
```
Error from server (Forbidden): error when creating "pod-privileged.yaml": pods "pod-nginx-privileged" is forbidden: violates PodSecurity "baseline:latest": privileged (container "nginx-container" must not set securityContext.privileged=true)
```
Applying the same privileged Pod manifest to the baseline namespace fails because this namespace enforces the baseline Pod Security Standard. Baseline *explicitly disallows privileged containers*, so the API server rejects the request before the Pod is created. This shows how enforce mode actively prevents insecure workloads from running.


### Creating a baseline-compliant nginx pod
```
kubectl apply -f pod-baseline.yaml -n baseline
```
Output:
```
Warning: would violate PodSecurity "restricted:latest": allowPrivilegeEscalation != false (container "nginx-container" must set securityContext.allowPrivilegeEscalation=false), unrestricted capabilities (container "nginx-container" must set securityContext.capabilities.drop=["ALL"]), runAsNonRoot != true (pod or container "nginx-container" must set securityContext.runAsNonRoot=true), seccompProfile (pod or container "nginx-container" must set securityContext.seccompProfile.type to "RuntimeDefault" or "Localhost")
```
The nginx Pod defined in *pod-baseline.yaml* removes the ***privileged=true*** setting, making it compliant with the baseline policy. Kubernetes allows the Pod to be created but emits warnings because the Pod does not meet the stricter restricted standard. These warnings explain exactly which additional security settings would be required to meet higher security expectations.

### Applying restricted security settings
```
kubectl apply -f pod-restricted.yaml -n baseline
```
After adding all required restricted settings, such as disabling privilege escalation, dropping Linux capabilities, enforcing non-root execution, and defining a seccomp profile—the Pod passes policy validation. However, Kubernetes fails the container at runtime because *the standard nginx image runs as root by default*, which conflicts with ***runAsNonRoot=true***. This highlights that Pod Security Standards validate intent, but the container image must also support those constraints.

```
kubectl describe pod pod-nginx-restricted -n baseline
```
Output
```
Warning  Failed     6s (x2 over 7s)  kubelet            spec.containers{nginx-container}: Error: container has runAsNonRoot and image will run as root (pod: "pod-nginx-restricted_baseline(a6eb8065-4049-4648-a553-b6ebe2672464)", container: nginx-container)
```

```
kubectl delete pod pod-nginx-restricted -n baseline
```
### Switching to an unprivileged nginx image
```
kubectl apply -f pod-restricted-unprivileged.yaml -n baseline
```
Using **nginxinc/nginx-unprivileged** resolves the issue because this image is explicitly designed to run as a non-root user. With both the Pod security context and the container image aligned, the Pod successfully runs in the baseline namespace under restricted security requirements. This demonstrates the importance of choosing security-aware container images.

### Cleanup Resources:
```
kubectl delete ns baseline privileged
```
Deleting the baseline and privileged namespaces removes all Pods, configurations, and policies associated with them in a single action. Namespace deletion is a clean and efficient way to tear down test environments and ensures no leftover resources remain in the cluster.
