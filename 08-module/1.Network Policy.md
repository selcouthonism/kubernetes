NetworkPolicy is a Kubernetes resource used to control how Pods communicate with each other and with external endpoints at the network level. By default, Kubernetes allows **all Pods to talk to all other Pods** across all namespaces, which is convenient but insecure. NetworkPolicies let you define explicit allow rules for traffic based on Pod labels, namespaces, IP blocks, ports, and protocols, effectively acting as a Kubernetes-native firewall for Pods.

At a high level, a NetworkPolicy works on a **default-deny** model. The moment a Pod is selected by any NetworkPolicy, **all traffic not explicitly allowed is denied**. Policies can control ingress (incoming traffic), egress (outgoing traffic), or both. Importantly, NetworkPolicies do not apply cluster-wide by default; they apply only to Pods matched by the policy’s selector and are enforced per namespace.

A NetworkPolicy is composed of four main parts. First, ***podSelector*** defines which Pods the policy applies to. Second, ***policyTypes*** specifies whether the policy controls ***Ingress***, ***Egress***, or both. Third, ingress rules define which sources (Pods, namespaces, or IP ranges) are allowed to connect to the selected Pods. Fourth, **egress rules** define which destinations the selected Pods are allowed to reach. Traffic that does not match these rules is dropped.

Selectors are central to NetworkPolicies. Pod selectors match Pods using labels, while namespace selectors allow traffic from or to Pods in specific namespaces. IP blocks allow or deny traffic from external networks using **CIDR ranges**, which is commonly used to restrict access to trusted subnets or block the public internet except for specific ranges.

NetworkPolicies are additive, not overriding. If multiple policies select the same Pod, the allowed traffic is the **union of all allowed rules** across those policies. This allows teams to layer policies. For example, one policy allowing DNS access and another allowing application-specific traffic—without conflicts.

NetworkPolicies rely on the ***Container Network Interface (CNI)*** plugin to be enforced. Not all CNIs support NetworkPolicy. Popular CNIs like *Calico*, *Cilium*, *Weave Net*, and *Antrea* fully support them, while basic setups may ignore policies entirely. If the CNI does not support NetworkPolicy, the resources can still be created, but they will have no effect.

From a security perspective, NetworkPolicies are a core part of Zero Trust networking in Kubernetes. They reduce the blast radius of compromised Pods, prevent lateral movement inside the cluster, and enforce strict boundaries between environments such as dev, staging, and prod. When combined with **RBAC (who can access the API)** and **Pod Security Standards (how Pods are allowed to run)**, NetworkPolicies complete the runtime security layer by controlling who can talk to whom at the network level.

## Create a new minikube with Calico CNI
```
minikube delete
minikube start -p netpol --cni calico
kubectl get pod -n kube-system
```
This step recreates the Minikube cluster using Calico as the CNI plugin, which is required because NetworkPolicies are enforced by the CNI, not Kubernetes itself. By deleting the existing cluster and starting a new one with ```--cni calico```, you ensure that ingress and egress rules will actually be applied. Verifying pods in the kube-system namespace confirms that core components and Calico are running correctly.

## NetworkPolicy (Ingress - Egress) 
### Create a deployment and service
Create a deployment and service:
```
kubectl apply -f deploy-color-api.yaml -f svc-color-api.yaml -f pod-alpine.yaml
```
Here, you deploy the *color-api* application, expose it internally using a Service, and create an Alpine-based debug pod for testing network connectivity. At this stage, no NetworkPolicy exists, so Kubernetes follows its default behavior: all Pods can communicate freely. This setup establishes a baseline where traffic is expected to succeed.

#### Test connectivity before NetworkPolicy
```
kubectl exec -it alpine-curl-pod -- sh
curl color-api-svc/api
```
By exec’ing into the Alpine pod and curling *color-api-svc/api*, you confirm that the service is reachable. This demonstrates the default “allow all” networking model in Kubernetes and provides a reference point to compare behavior after NetworkPolicies are applied.

### Ingress Traffic

#### Define a deny-all ingress policy
```
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: np-deny-all-ingress
spec:
  podSelector: {} # Selects all pods in the namespace
  policyTypes:
  - Ingress
```
This NetworkPolicy uses an empty ***podSelector: {}***, which selects all Pods in the namespace, and specifies Ingress as the policy type with no allowed rules. Once applied, this means that no Pod is allowed to receive inbound traffic, unless another policy explicitly allows it. Outbound traffic is still permitted because egress is not restricted.

#### Apply and inspect the NetworkPolicy
```
kubectl apply -f np-deny-all-ingress.yaml
kubectl describe networkpolicy np-deny-all-ingress
```
Applying the deny-all ingress policy activates the restriction, and describing it confirms that it applies to all Pods. From this point forward, any incoming connections to Pods in the namespace are blocked by default.

#### Observe blocked ingress traffic
```
kubectl exec -it alpine-curl-pod -- sh
curl color-api-svc/api # No response
```
When the Alpine pod tries to curl the color-api service again, the request fails. This is because the client Pod is allowed to send traffic, but the color-api Pod is not allowed to receive it due to the ingress deny-all policy. This clearly illustrates how ingress rules control traffic at the destination Pod.

#### Verify egress traffic is still allowed
```
curl https://catfact.ninja/fact
```
Curling an external site like *catfact.ninja* succeeds, proving that egress traffic is unaffected by an ingress-only policy. This distinction is important: ingress and egress controls are independent in Kubernetes.

#### Allow ingress from specific Pods
Allow ingress traffic from *app: alpine-curl* or *tier: backend*:
```
  podSelector:
    matchLabels:
      app: color-api
  policyTypes:
  - Ingress
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: alpine-curl
    - podSelector:
        matchLabels:
          tier: backend
```
This policy selectively allows ingress to Pods labeled **app: color-api** only from Pods with labels **app: alpine-curl** or **tier: backend**. By narrowing access using labels, you move from a broad deny-all stance to a least-privilege allowlist model, which is a best practice for Pod-to-Pod security.

#### Apply allow policy and retest
```
kubectl apply -f np-allow-alpine-pod.yaml

kubectl exec -it alpine-curl-pod -- sh
curl color-api-svc/api # Successful
```
After applying the policy, the Alpine pod with the correct label can successfully reach the *color-api* service. This confirms that NetworkPolicies are additive and that explicitly allowed traffic now passes through.

#### Create additional Alpine Pods
Create another alpine pod:
```
kubectl apply -f pod-alpine2.yaml -f pod-alpine3.yaml
```
New Alpine Pods with different labels are introduced to test selector-based filtering. This step is designed to show that labels matter, and only Pods matching the allowed selectors can access the service.

#### Test access from new Pods
```
kubectl exec -it alpine-curl-pod-2 -- sh
curl color-api-svc/api # No Response

kubectl exec -it alpine-curl-pod-3 -- sh
curl color-api-svc/api # Successful
```
The second Alpine pod fails to connect because its labels do not match the policy, while the third succeeds because it does. This demonstrates fine-grained access control using Pod labels.

#### Allow traffic via namespace selectors
Allow traffic-generator pods from 'dev' namespace.
Update *np-allow-alpine-pod.yaml* with:
```
- namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: dev
      podSelector:
        matchLabels:
          app: traffic-generator
```
```
kubectl apply -f np-allow-alpine-pod.yaml
```
The policy is extended to allow traffic from Pods in the *dev* namespace that match a specific label. Namespace selectors enable cross-namespace communication control, which is critical in multi-environment clusters where teams share infrastructure.

#### Create dev namespace and Pods
```
kubectl apply -f ns-dev.yaml -f pod-alpine4-ns-dev.yaml -f pod-traffic-generator-ns-dev.yaml
```
By creating Pods in the *dev* namespace, you test whether namespace-based rules work as expected. The Alpine pod without the correct label is denied, while the traffic generator Pod is allowed.

```
kubectl exec -it alpine-curl-pod-4 -n dev -- sh
curl color-api-svc.default.svc.cluster.local/api # No response
```

#### Observe traffic-generator behavior
```
kubectl logs -f traffic-generator-pod -n dev
```
Checking the logs of the traffic generator confirms that only Pods explicitly permitted by the NetworkPolicy can reach the *color-api* service, reinforcing the concept of controlled ingress across namespaces

### Cleanup ingress resources
```
kubectl delete -f deploy-color-api.yaml -f svc-color-api.yaml -f pod-alpine.yaml -f pod-alpine2.yaml -f pod-alpine3.yaml -f ns-dev.yaml -f pod-alpine4-ns-dev.yaml -f pod-traffic-generator-ns-dev.yaml
```

```
kubectl delete -f np-deny-all-ingress.yaml -f np-allow-alpine-pod.yaml 
```
All deployed workloads and NetworkPolicies are deleted to return the cluster to a clean state. This is important to avoid policy conflicts when moving on to egress examples.

### Egress Traffic
#### Create Alpine pod before applying egress policy
The Alpine pod is created first so it can install curl successfully. This is necessary because applying a deny-all egress policy beforehand would block internet access, causing the container to crash during package installation.
```
kubectl apply -f pod-alpine.yaml
```
If deny egress rules applied before *alpine-curl-pod* creation, the pod will be crashing due to the *np-deny-all* network policy, which denies all ingress and egress traffic for all pods (since podSelector: {} selects everything and no egress rules are defined). This prevents ```apk update && apk add curl``` from accessing the internet to download packages, causing the command to fail (exit code 4).

#### Apply deny-all ingress and egress policy
```
kubectl apply -f np-deny-all.yaml
```
This policy blocks all inbound and outbound traffic for all Pods. Once applied, Pods cannot reach internal services, external services, or even DNS, unless explicitly allowed.

#### Observe blocked egress traffic
```
kubectl exec -it alpine-curl-pod -- sh
curl www.google.com # Cannot make a call
```
Curling an external site like Google fails, confirming that egress traffic is now restricted. This highlights how egress policies control what destinations a Pod is allowed to contact.

#### Allow egress from Alpine to color-api
```
  podSelector:
    matchLabels:
      app: alpine-curl
  policyTypes:
  - Egress
  egress:
  - to:
    - podSelector:
        matchLabels:
          app: color-api
```
```
kubectl apply -f np-allow-egress.yaml -f np-allow-alpine-pod.yaml
```
An egress policy is defined that allows the Alpine pod to send traffic only to Pods labeled *app: color-api*. This enables direct **Pod-to-Pod communication by IP** but does not yet allow service-based access.

#### Test direct Pod IP access
```
kubectl get pods color-api-68db8c6b79-cbbgm -o jsonpath='{.status.podIP}' # 10.244.28.167
kubectl exec -it alpine-curl-pod -- sh
curl 10.244.28.167 # Successful
curl color-api-svc/api # Cannot access via service
```
Curling the color-api Pod IP succeeds, but accessing it through the Service name fails. This happens because **DNS resolution is still blocked**, which is required for service discovery.

#### Allow egress to DNS
```
  podSelector: {}
  policyTypes:
  - Egress
  egress:
  - to:
    - namespaceSelector:
        matchLabels:
        # kubectl describe ns kube-system
          kubernetes.io/metadata.name: kube-system
      podSelector:
        matchLabels:
          k8s-app: kube-dns
```
```
kubectl apply -f np-allow-egress-dns.yaml
```
A policy is added to **allow egress traffic to CoreDNS Pods** in the kube-system namespace. DNS is a foundational dependency in Kubernetes, and without it, Services cannot be resolved.

#### Verify service access works
```
kubectl get pods color-api-68db8c6b79-cbbgm -o jsonpath='{.status.podIP}' # 10.244.28.167
kubectl exec -it alpine-curl-pod -- sh
curl 10.244.28.167 # Successful
curl color-api-svc/api # Successful
```
After DNS egress is allowed, the Alpine pod can access the color-api service using its Service name. This demonstrates how multiple egress rules must be combined to enable real-world communication.

### Cleanup egress resources
```
kubectl delete -f deploy-color-api.yaml -f pod-alpine.yaml -f svc-color-api.yaml -f policies/np-deny-all.yaml -f policies/np-allow-egress-dns.yaml -f policies/np-allow-alpine-pod.yaml 
```
All workloads and NetworkPolicies are deleted, restoring the cluster to its default networking behavior. This final cleanup ensures no residual policies affect future experiments.
