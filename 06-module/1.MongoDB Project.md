## Prepare MongoDB Database

### Creating Credentials
```
kubectl apply -f mongodb-root-creds.yaml -f mongodb-colordb-creds.yaml
```
Applying *mongodb-root-creds.yaml* and *mongodb-colordb-creds.yaml* creates two separate Secrets: one holding the MongoDB root credentials and another holding the application-level database credentials. This separation allows MongoDB to initialize with full administrative access while ensuring that application Pods later authenticate using limited, least-privilege credentials scoped only to the colordb database.

### Security Best Practice
Root credentials (root_user / root_password) and application credentials (colordb_user / colordb_password) should be stored in two separate Kubernetes Secret manifests because they serve different purposes, have different risk profiles, and should be governed by different access and lifecycle rules.

#### Principle of Least Privilege
Root credentials typically grant full administrative access to a database (create/drop databases, manage users, change schemas), while application credentials are scoped to only what the app needs (read/write specific tables or schemas). Storing them in separate Secrets ensures the application can be granted access only to the app-level Secret, preventing accidental or malicious use of root-level privileges inside application Pods.

#### Blast Radius Reduction
If an application Pod is compromised and both root and app credentials live in the same Secret, an attacker immediately gains full database control. By separating Secrets, even a successful breach limits the damage to the application’s restricted permissions, significantly reducing the blast radius of a security incident.

#### Different Access Controls (RBAC)
Kubernetes RBAC can be applied at the Secret level. Infrastructure components (database init Jobs, migrations, or operators) can be allowed to read the root Secret, while application Deployments can only access the app Secret. This clean separation makes RBAC policies simpler, safer, and easier to audit.

#### Different Lifecycle and Rotation Policies
Root credentials are usually long-lived and rotated rarely, while application credentials may be rotated more frequently or per environment. Keeping them in separate manifests avoids unnecessary application restarts or redeployments when only root credentials change, and allows independent rotation strategies.

#### Separation of Responsibilities
In real-world teams, database administrators or platform engineers manage root credentials, while application teams manage app-level credentials. Separate Secret manifests reflect this organizational boundary and reduce the risk of developers unintentionally handling or exposing root-level secrets.

#### Reduced Accidental Exposure
Application Secrets are often mounted into Pods, logged during debugging, or referenced in CI/CD pipelines. Root credentials should never be exposed in these contexts. Separate Secret files help prevent accidental inclusion of root credentials in application manifests or logs.

#### Clear Intent and Auditing
Having distinct Secrets like db-root-creds and colordb-app-creds makes intent explicit. Auditors and engineers can immediately understand which Secret is powerful and which is safe for application use, improving maintainability and compliance.

#### Summary
Keeping root and application credentials in separate Secret manifests enforces least privilege, limits security impact, enables clean RBAC and rotation policies, supports team boundaries, and aligns with Kubernetes and security best practices.

### Creating a Headless Service and ConfigMaps
```
kubectl apply -f mongodb-svc.yaml -f mongodb-init-colordb.yaml
```
Applying *mongodb-svc.yaml* creates a headless Service, which provides stable DNS identities for each MongoDB Pod in the StatefulSet, while *mongodb-init-colordb.yaml* creates a ConfigMap containing the **init-db.js** script. This script is mounted into MongoDB’s initialization directory so it runs automatically on first startup, creating the colordb database and its restricted user using values injected from Secrets via environment variables.

#### Verifying Prerequisites Before StatefulSet Creation
Running ```kubectl get secret,configmap,svc``` confirms that all dependencies (Secrets for credentials, the ConfigMap for initialization logic, and the headless Service for stable networking) exist before creating the StatefulSet. This ensures MongoDB Pods can start successfully without missing configuration or credentials.

### Creating the StatefulSet
```
kubectl apply -f mongodb-statefulset.yaml
```
Applying *mongodb-statefulset.yaml* creates a MongoDB StatefulSet with stable Pod names, persistent storage, and predictable startup behavior. Each Pod receives its own ***PersistentVolumeClaim***, mounts the initialization script, and runs MongoDB with the root credentials so the init script can safely create the application database and user during the first startup.

A StatefulSet, combined with a Headless Service, is the perfect combination here. The StatefulSet gives each pod a unique, stable identity, and the Headless Service allows your API to directly discover and connect to each individual MongoDB instance by its unique network identifier, rather than going through a single load-balanced IP.

The ***volumeClaimTemplate*** within a StatefulSet is precisely what allows for dynamic provisioning. When a new pod is created by the StatefulSet, it uses this template to automatically create a **Persistent Volume Claim (PVC)**. This PVC then requests a Persistent Volume (PV) from the available storage, and if dynamic provisioning is enabled, a PV is automatically created and bound to that PVC. This ensures that each pod in your StatefulSet gets its own dedicated, persistent storage that remains even if the pod is deleted or rescheduled.

#### Stateles vs Stateful applications
Stateless applications are easily replaceable and scalable because they don't hold onto unique data or session information between requests. Their pods can be freely created, destroyed, and scaled without impacting the application's state.

Stateful applications, on the other hand, maintain a unique state, often involving persistent data, which makes their pods less interchangeable and requires careful management during scaling or replacement. This is why we use specific resources like StatefulSets for them.

#### Inspecting Pods, Volumes, and Initialization
```
kubectl get statefulset,pods,pv,pvc
kubectl logs mongodb-ss-0
kubectl exec -it mongodb-ss-0 -- sh
cat docker-entrypoint-initdb.d/init-db.js
```
Checking StatefulSets, Pods, PVs, and PVCs verifies that each MongoDB replica has its own dedicated storage. Viewing the logs and inspecting ***/docker-entrypoint-initdb.d/init-db.js*** inside the Pod confirms that the initialization script was correctly injected and executed during the first container startup.

#### Authenticating and Verifying Access Control
```
kubectl exec -it mongodb-ss-0 -- mongosh
show dbs # MongoServerError[Unauthorized]
use admin
db.auth('root_user','root_password') # { ok: 1 }
show dbs # admin config local

use colordb
db.auth('colordb_user','colordb_password') # { ok: 1 }
db.testCollection.insertOne({hello: 'world'})
db.testCollection.find()

use otherdb
db.testCollection.insertOne({hello: 'world'}) # MongoServerError[Unauthorized]
exit
```
Connecting with ***mongosh*** demonstrates MongoDB’s security model in action: unauthenticated access is denied, root credentials allow access to administrative databases, and the application user can authenticate only to *colordb*. Attempts to write to other databases fail, proving that the application credentials are correctly restricted.

```
kubectl scale statefulset mongodb-ss --replicas=3
```
Scaling the StatefulSet to three replicas creates two additional Pods, each with its own PVC and PV. This shows how StatefulSets guarantee one-to-one relationships between Pods and storage, ensuring data isolation and persistence even as replicas are added.

#### Validating Storage Isolation
```
minikube ssh
ls /tmp/hostpath-provisioner/default/
```
Inspecting Minikube’s host path directories confirms that each Pod’s data is stored separately on disk. When *mongodb-ss-1* queries *colordb*, it sees no data written by *mongodb-ss-0*, proving that each replica has its own independent volume and does not share data by default.

mongodb-ss-1 cannot access the data from  mongodb-ss-0:
```
kubectl exec -it mongodb-ss-1 -- mongosh
use colordb
db.auth('colordb_user','colordb_password') # { ok: 1 }
db.testCollection.find() # returns nothing
```

### Scaling the StatefulSet Down
```
kubectl scale statefulset mongodb-ss --replicas=1
```
Scaling the StatefulSet back to one replica terminates the extra Pods but leaves their PVCs and PVs intact. This behavior protects data from accidental loss and allows replicas to be recreated later with their original storage.

#### Manual Cleanup of Persistent Volumes
```
kubectl delete pvc mongodb-data-mongodb-ss-1 mongodb-data-mongodb-ss-2
```
Manually deleting the unused PVCs removes the associated ***PersistentVolumes***, fully cleaning up storage resources that are no longer needed. This step is necessary because StatefulSets intentionally do not delete PVCs automatically, giving operators explicit control over data retention.

## Update color-api application

### Building and Publishing color-api v2.0.0
```
docker build -t selcouthonism/color-api-image:2.0.0 .
docker push selcouthonism/color-api-image:2.0.0
```
The ```docker build``` and ```docker push``` commands create a new container image for color-api version 2.0.0 and publish it to the container registry. This step packages the updated application code, including new REST endpoints and database logic, into an immutable image so Kubernetes can deploy the exact same version consistently across all Pods.

### Deploying the Updated Application
```
kubectl apply -f color-api-deployment.yaml -f color-api-svc.yaml
```
Applying *color-api-deployment.yaml* and *color-api-svc.yaml* ensures that the color-api Pods are created using the new 2.0.0 image and that a Service exposes them inside the cluster. This step assumes the database is already running, allowing the application to connect immediately on startup and perform CRUD operations against persistent storage.

#### Verifying Pod Startup and Logs
```
kubectl get pods
kubectl logs color-api-fff674ff5-5ghpx
```
Running ```kubectl get pods``` confirms that the new Pods are running, while checking the logs validates that the application started successfully, connected to the database, and registered the new API routes. This step is critical to catch configuration or connection errors before exposing the service.

#### Exposing the Service via Minikube
```
minikube service color-api-svc
# http://127.0.0.1:55767
```
The ```minikube service color-api-svc``` command exposes the Kubernetes Service to your local machine and provides a temporary URL. This allows you to interact with the application from outside the cluster without setting up an Ingress or LoadBalancer, making it ideal for local development and testing.

#### Creating New Colors with POST
```
curl -i -X POST http://127.0.0.1:55767/api/color/green -H "Content-Type: application/json" -d '{"value": "#00FF00", "description": "A bright green color"}'

curl -X POST http://127.0.0.1:55767/api/color/blue -H "Content-Type: application/json" -d '{"value": "#0000FF", "description": "A deep blue color"}'
```
The ```POST /api/color/:key``` requests test the ability of the new version to insert data into the database. If a color key does not already exist, the application persists the color value and description, verifying that create operations and database writes are functioning correctly.

#### Updating Existing Colors with PUT
```
curl -X PUT http://127.0.0.1:55767/api/color/green -H "Content-Type: application/json" -d '{"value": "#008000", "description": "Updated green color - darker shade"}'
```
The ```PUT /api/color/:key``` request confirms update behavior by modifying an existing color entry. This step validates idempotent update logic, ensuring that the application correctly finds existing records and updates them rather than creating duplicates.

```
curl http://127.0.0.1:55767

The ```GET /api``` endpoint tests read functionality and optional query handling. When a **colorKey** parameter is provided, the response includes the stored color and the Pod hostname, demonstrating both successful database reads and load-balanced service behavior across replicas.

#### Listing All Colors
```
curl -i http://127.0.0.1:55767/api/color
```
Calling ```GET /api/color``` verifies that the application can retrieve and return all stored color records from the database. This ensures collection-level queries work as expected and confirms overall data consistency.

#### Fetching a Single Color by Key

```
The ```GET /api/color/:key``` request validates key-based lookups and proper HTTP semantics. A successful response returns the color details, while a missing key correctly results in a 404, confirming robust error handling.
