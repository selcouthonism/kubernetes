# ConfigMaps
A ConfigMap is a Kubernetes object used to **store non-sensitive configuration data** separately from application code and container images. It allows you to externalize configuration such as environment variables, application settings, feature flags, or configuration files, making applications easier to manage and update without rebuilding images. ConfigMaps support better portability and reuse of the same container image across multiple environments like dev, test, and production.

ConfigMaps can be consumed by Pods in multiple ways: 
- as environment variables, 
- as command-line arguments, 
- as mounted files in a volume. 

When mounted as files, each key becomes a file whose content is the corresponding value, which is ideal for application config files. This flexibility enables dynamic configuration management while keeping containers immutable and aligned with cloud-native best practices.

- Data cannot exceed 1MB in size.
- Pods must be in the same namespace as the ConfigMaps they reference. **Exception:** when fetching values directly via the Kubernetes API.

### Update the color-api application and build the new image
```
docker build -t selcouthonism/color-api-image:1.3.0 .
docker push selcouthonism/color-api-image:1.3.0
```
In this step, the color-api application is updated to accept external configuration for color and file paths using environment variables such as **DEFAULT_COLOR** and **COLOR_CONFIG_PATH**. Building and pushing the 1.3.0 image packages this new behavior into a reusable container image that can be configured dynamically at runtime without rebuilding it again.

### Passing Information from ConfigMaps via Environment Variables

#### Create a ConfigMap for environment-based configuration
```
kubectl apply -f configmap-color-api-red.yaml
```
Applying configmap-color-api-red.yaml creates a ConfigMap that stores configuration data—in this case, the color value *red*.

```
kubectl get configmap
kubectl get configmap color-api-config-red -o yaml
kubectl describe configmap ccolor-api-config-red
```
Listing and describing the ConfigMap confirms that Kubernetes has stored the key-value pairs correctly and makes them available for injection into Pods.

#### Understand ConfigMap Injection Strategies
Kubernetes provides two primary ways to inject ConfigMap data into containers: 
- The bulk approach (envFrom)
- The granular approach (env with valueFrom) 

**The bulk approach** automatically injects all keys as environment variables, which is convenient for large sets of general configuration, while **the granular approach** allows precise control over which keys are exposed and how they are named inside the container.

You'll choose between these based on how much control you need over the mapping and how much "clutter" you're willing to accept in your container's environment.

##### 1. The Bulk Approach: envFrom
The ***envFrom*** field is used when you want to take every single key-value pair inside a ConfigMap and turn them into environment variables automatically.

ConfigMap:
```
COLOR: red
```

Inside Pod:
```
envFrom:
- configMapRef:
    name: color-api-config
```

- **How it works:** If your color-api-config ConfigMap contains DEBUG=true and PORT=8080, your container will automatically have those variables available.
- **The Mapping:** The environment variable name in the container will be identical to the key name in the ConfigMap (variable names must match keys).
- **Best for:** General application settings where you have dozens of variables and don't want to list them all manually in the YAML.

You can add an optional prefix field to envFrom. For example, a prefix of APP_ would turn a ConfigMap key of PORT into an environment variable named APP_PORT. This helps avoid naming collisions with system variables.

##### 2. The Granular Approach: env with valueFrom
The ***env*** block is used for explicit mapping. You are picking one specific key from a ConfigMap and assigning it to a specific environment variable name of your choosing.

ConfigMap:
```
DEFAULT_COLOR: red
```

Inside Pod:
```
env:
- name: DEFAULT_COLOR
    valueFrom:
    configMapKeyRef:
        name: color-api-config
        key: COLOR
```

- **How it works:** In this example, we are looking into the color-api-config ConfigMap, finding the key named COLOR, and assigning its value to a new environment variable inside the container called DEFAULT_COLOR.
- **The Mapping:** This decouples the ConfigMap key from the environment variable name.
- **Best for: * Renaming:** When your application code expects DEFAULT_COLOR, but the infrastructure team named the ConfigMap key COLOR.
- **Precision:** When a ConfigMap contains 50 keys, but this specific container only needs one of them (Principle of Least Privilege).
- **Use the granular env approach for precise mapping:** By explicitly mapping the COLOR key from the ConfigMap to the DEFAULT_COLOR environment variable, this step demonstrates decoupling application expectations from infrastructure naming. This approach follows the principle of least privilege by exposing only the required configuration and ensuring compatibility with existing application code.

#### Create a Pod that consumes the ConfigMap via environment variables
Create a pod that reads env value with "env":
```
kubectl apply -f pod-color-api-with-configmap-red.yaml
```
Applying pod-color-api-with-configmap-red.yaml creates a Pod where the ConfigMap value is injected as an environment variable.

```
kubectl describe pod color-api-pod-red

# Environment:
#   DEFAULT_COLOR:  <set to the key 'COLOR' of config map 'color-api-config-red'>  Optional: false
```
Describing the Pod verifies that DEFAULT_COLOR is correctly sourced from the ConfigMap, confirming successful configuration injection.

#### Expose the Pod and verify runtime behavior
```
kubectl expose pod color-api-pod-red
kubectl get svc color-api-pod-red
minikube service color-api-pod-red
```
Exposing the Pod as a Service and accessing it via Minikube validates that the application is reading the environment variable correctly. The API response reflecting the red color confirms that external configuration is working as intended.

### Mount a ConfigMap as Files in a Volume
```
kubectl apply -f configmap-color-api-green.yaml -f pod-color-api-with-configmap-green.yaml
```
Applying the green ConfigMap and Pod manifests demonstrates the second consumption pattern: **mounting ConfigMap data as files**. Kubernetes projects each key in the ConfigMap into the filesystem, making it accessible to the container as configuration files or scripts.

#### Inspect mounted configuration files inside the container
```
kubectl exec -it color-api-pod-green -c color-api-container -- sh

ls /mnt/config
# COLOR_CONFIG_PATH  hello-from-green.js color.txt

cat /mnt/config/color.txt
node /mnt/config/hello-from-green.js
```
Exec’ing into the container and listing /mnt/config shows the files created from the ConfigMap. Reading color.txt and executing the JavaScript file confirms that applications can consume ConfigMap data as regular files, which is ideal for file-based configuration.

#### Expose the Pod and validate file-based configuration
```
kubectl expose pod color-api-pod-green
kubectl get svc color-api-pod-green
minikube service color-api-pod-green
```
Exposing the Pod and accessing the service confirms that the application correctly reads configuration from mounted files. This step verifies the flexibility of ConfigMaps for different configuration consumption patterns.

### Combine environment variables and mounted files
```
kubectl apply -f configmap-color-api-purple.yaml -f pod-color-api-with-configmap-purple.yaml
```
Using two ConfigMaps—one for environment variables and one for mounted files—demonstrates a hybrid approach. This allows sensitive or frequently accessed values to be injected as environment variables while larger or structured configuration is provided as files.

#### Verify combined configuration inside the container
```
kubectl exec -it color-api-pod-purple -c color-api-container -- sh

ls /mnt/config
# hello-from-purple.js color.txt

cat /mnt/config/color.txt
node /mnt/config/hello-from-purple.js
```
Inspecting the mounted directory and reading the configuration files confirms that both injection mechanisms work together seamlessly. This pattern is common in real-world applications that require mixed configuration types.

### Cleanup Resources
```
kubectl delete -f configmap-color-api-red.yaml -f pod-color-api-with-configmap-red.yaml -f configmap-color-api-green.yaml -f pod-color-api-with-configmap-green.yaml -f configmap-color-api-purple.yaml -f pod-color-api-with-configmap-purple.yaml
```
Deleting the ConfigMaps and Pods removes all configuration and application resources created during the example. This final step ensures the cluster is returned to a clean state and reinforces good resource hygiene practices.
