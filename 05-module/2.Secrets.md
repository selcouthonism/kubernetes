# Secrets
Secrets in Kubernetes are objects designed to store and manage sensitive information such as passwords, API keys, tokens, certificates, and private keys. They allow you to decouple confidential data from application code, container images, and Pod specifications, reducing the risk of accidental exposure. While Secrets are **base64-encoded** (not encrypted by default), Kubernetes provides mechanisms like RBAC, encryption at rest, and tight access controls to improve their security.

Secrets can be consumed by Pods in several ways: 
- as environment variables, 
- as mounted files in volumes, or 
- via image pull secrets for authenticating to private registries. 

When mounted as files, Kubernetes ensures proper permissions and can update the content dynamically, making this approach ideal for certificates and keys. Using Secrets is a best practice for handling sensitive configuration securely and consistently across environments while keeping applications cloud-native and compliant.

Clous providers and their managed Kubernetes offerings normally provide native integration with secrets managers for improved and more secure secret storage.

## Best Practices

### Encryption at Rest
When we talk about secrets "in rest," we're referring to secrets that are stored and not actively being used. Since Base64 encoding isn't encryption, Kubernetes itself doesn't encrypt secrets by default when they are stored in etcd (the Kubernetes backing store).

You would need to implement encryption at rest for your **etcd** database. This typically involves configuring etcd to encrypt its data, or using a solution like a Key Management Service (KMS) to encrypt the secrets before they are stored in etcd.

### Role-Based Access Control (RBAC)
RBAC allows you to define specific roles with permissions to perform actions on Kubernetes resources, including secrets. You can then bind these roles to users or service accounts.

For example, you could create a role that only allows read access to certain secrets for a specific application's service account, and a different role that allows an administrator to create and update secrets. This ensures that only authorized entities can interact with sensitive data, adhering to the principle of least privilege.

### Only access the specific secret data
When mounting secrets as volumes, you can specify individual secretKeyRef entries within the pod specification to ensure that only the necessary keys from a secret are exposed to the container, rather than the entire secret object.

This minimizes the attack surface and adheres to the principle of least privilege, even within the pod itself.

### Security Best Practices
Beyond RBAC and limiting secret exposure, you should also consider:

- **Namespace Isolation:** Placing ConfigMaps and Secrets in dedicated namespaces can help restrict access and prevent accidental exposure to other applications.
- **Auditing and Logging:** Implementing robust auditing and logging for access to ConfigMaps and Secrets can help detect and investigate unauthorized access attempts.
- **Secret Rotation:** Regularly rotating secrets (changing them periodically) reduces the window of opportunity for a compromised secret to be exploited.
- **External Secret Management:** For highly sensitive data, integrating with external secret management systems (like HashiCorp Vault or cloud provider KMS) can provide advanced features like centralized management, automatic rotation, and stronger encryption.

Before even deploying secrets to Kubernetes, the very first step you should take is to ensure that the secrets themselves are never hardcoded directly into application code or committed to version control systems (like Git). This is a fundamental security principle. Instead, they should be injected into the application at runtime, using mechanisms like the Kubernetes Secrets.

Deleting secrets and ConfigMaps when they are no longer needed is a critical part of good hygiene and security. This prevents stale or unused sensitive data from lingering in the cluster, reducing potential attack vectors.

## Create a Secret with kubectl cli
### Viewing Secret creation commands and options
The ```kubectl create secret --help``` and ```kubectl create secret generic --help``` commands are used to explore how Secrets can be created and which flags are available. These help outputs explain supported Secret types, input methods (literals, files, directories), and namespace scoping, giving you an overview before creating Secrets so you choose the correct type and approach for your use case.

### Understanding Secret types
Kubernetes supports multiple Secret types to match common security needs: **docker-registry** Secrets store credentials for private container registries and are referenced during image pulls; **generic** (Opaque) Secrets hold arbitrary key–value data such as usernames or API keys; and **tls** Secrets are designed specifically for TLS certificates and private keys, enabling secure HTTPS and mTLS configurations.

- **docker-registry** type secret is for accessing a container registry. Create a secret for use with a Docker registry.
- **generic** type secret indicate an Opaque secret type. Create a secret from a local file, directory, or literal value.
- **tls** type secret holds TLS certificate and its associated key. Create a TLS secret.

### Generating a Secret from literals
```
kubectl create secret generic db-creds --from-literal=username=db_user --from-literal=password=db_pass
```
This command is used to manually create a **Kubernetes Secret** object named *db-creds* directly from the command line. When you run this command, the Kubernetes API server creates an object where the values (db_user and db_pass) are stored as Base64 encoded strings. 

Kubernetes stores each literal as a key–value pair, Base64-encodes the values, and persists them in etcd, making this method quick for testing or simple setups without external files.

**Note on Security:** It is important to remember that Base64 is not encryption; it is simply encoding. To truly secure these at rest, you should enable "Encryption at Rest" in your K8s cluster (using a provider like AWS KMS or HashiCorp Vault).

- **kubectl create secret**: The base command to create a Secret resource in the cluster.
- **generic**: Specifies the type of secret. generic (or Opaque) is the most common type, used for arbitrary user-defined data like database passwords or API keys.
- **db-creds**: The unique name of the Secret object within the current namespace
- **--from-literal=...**: A flag that allows you to define a key-value pair directly. In this case, it creates two entries: username and password.

#### Inspecting and decoding the Secret
```
kubectl get secrets
kubectl describe secret db-creds
kubectl get secret db-creds -o yaml
# password: ZGJfcGFzcw== username: ZGJfdXNlcg==
echo "ZGJfdXNlcg==" | base64 -d
```
Using ```kubectl get secrets```, ```kubectl describe secret db-creds```, and ```kubectl get secret db-creds -o yaml``` allows you to verify that the Secret exists and inspect its structure. The YAML output shows Base64-encoded values, and decoding them with ```base64 -d``` demonstrates that the data is not encrypted by default, highlighting the importance of enabling encryption at rest for production clusters.

### Injecting Secrets as environment variables
```
kubectl apply -f pod-busybox-with-secret-env.yaml
```
Applying pod-busybox-with-secret-env.yaml creates a Pod that consumes the Secret using ***env*** or ***envFrom***, injecting Secret values as environment variables inside the container. This method is simple and commonly used, allowing applications to read credentials from environment variables without accessing the filesystem.

#### Verifying Secret injection via environment variables
```
kubectl logs busybox-with-secret-as-env-vars
# DB User is db_user DB Password is db_pass

kubectl describe pod busybox-with-secret-as-env-vars
kubectl get pod busybox-with-secret-as-env-vars -o yaml
```
Running ```kubectl logs``` and ```kubectl describe pod``` confirms that the Secret values are correctly injected and visible to the container at runtime. Inspecting the Pod’s YAML shows how the Secret keys map to environment variables, helping you understand the exact wiring between the Pod spec and the Secret.

### Injecting Secrets via a volume
```
kubectl apply -f pod-busybox-with-secret-volume.yaml
```
Applying pod-busybox-with-secret-volume.yaml mounts the Secret as a volume, where each key becomes a file containing the decoded value. This approach is preferred for certificates, keys, or applications that expect configuration files rather than environment variables, and Kubernetes automatically manages file permissions and updates.

#### Accessing Secret data from the mounted volume
```
kubectl exec -it busybox-with-secret-via-volume -- sh
ls /etc/db
# password  username
cat /etc/db/username
```
By executing into the container and listing **/etc/db**, you can see individual files such as *username* and *password*. Reading these files confirms that the Secret data is available as plain text inside the container, but only within the Pod’s security boundaries.

### Injecting specific Secret keys using volume items
```
kubectl apply -f pod-busybox-with-secret-volume-item.yaml
```
Applying pod-busybox-with-secret-volume-item.yaml demonstrates fine-grained control by **mounting only selected keys** from the Secret and placing them at custom paths. The items field maps a specific key (for example, password) to a desired file path, which is useful for organizing secrets or limiting exposure.

Volumes in the pod:
```
containers:
- name: busybox
  image: busybox:latest
  command: ["sh", "-c", "sleep 3600"]
  volumeMounts:
- name: db-credentials
    mountPath: /etc/db
    readOnly: true
volumes:
- name: db-credentials
  secret:
    secretName: db-creds
    items:
    - key: password 
    path: dev/password
```

#### Verifying volume item mapping
```
kubectl exec -it busybox-with-secret-via-volume-item -- sh
ls /etc/db/dev
# password
cat /etc/db/dev/password
```
Executing into the Pod and inspecting */etc/db/dev/password* confirms that only the specified key is mounted and accessible. This approach improves security and clarity by exposing only what the application truly needs.

### Cleanup Resources
```
kubectl delete -f pod-busybox-with-secret-env.yaml -f pod-busybox-with-secret-volume.yaml -f pod-busybox-with-secret-volume-item.yaml
kubectl delete secret db-creds
```
The cleanup commands remove the Pods and the db-creds Secret from the cluster, ensuring no sensitive data or test resources remain. Regular cleanup is a good practice to avoid orphaned Secrets and reduce the risk of accidental exposure in shared environments.
