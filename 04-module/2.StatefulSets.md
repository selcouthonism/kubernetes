# StatefulSet

A StatefulSet is a Kubernetes workload resource designed for managing stateful applications that require stable network identities, persistent storage, and ordered deployment behavior. Unlike Deployments, which treat Pods as interchangeable, StatefulSets assign each Pod a unique, predictable name (such as app-0, app-1) and maintain that identity across restarts. This makes StatefulSets ideal for databases, message brokers, and distributed systems where **each instance must be uniquely identifiable**.

StatefulSets tightly integrate with Persistent Volume Claims, typically using ***volumeClaimTemplates*** to automatically create a dedicated PVC for each Pod. These volumes persist even if a Pod is deleted or rescheduled, ensuring data durability. Additionally, StatefulSets support ordered startup, scaling, and termination, **allowing Pods to be created or removed in sequence**, which is critical for systems that rely on leader election, replication, or quorum-based behavior.

## Example
### Statically Provisioned Persistent Volumes

#### Prepare node directories for static local volumes
```
minikube ssh
sudo mkdir /mnt/disks/ss-0 /mnt/disks/ss-1 /mnt/disks/ss-2
sudo chmod 777 /mnt/disks/ss-0 /mnt/disks/ss-1 /mnt/disks/ss-2
exit
```
This step creates physical directories on the Minikube node that will back statically provisioned local Persistent Volumes. Local PVs require the target paths to already exist on the node, and setting permissive permissions ensures Pods can read and write data. This establishes the actual storage locations before Kubernetes objects are created.

#### Create statically provisioned Persistent Volumes
```
kubectl apply -f ss-persistent-volumes.yaml
```
Applying ss-persistent-volumes.yaml registers three local Persistent Volumes (ss-0, ss-1, ss-2) with Kubernetes, each mapped to a specific node directory. These PVs are independent of Pods and advertise fixed capacity, access modes, and a Retain reclaim policy. At this point, the volumes are available for binding but not yet in use.

#### Create a StatefulSet with two Pods
```
kubectl apply -f ss-statefulset-static.yaml
```
Applying ss-statefulset-static.yaml creates a StatefulSet that requests storage via ***volumeClaimTemplates***. Kubernetes automatically creates one Persistent Volume Claim per Pod and binds each claim to a matching static PV. The StatefulSet ensures predictable Pod names (demo-ss-0, demo-ss-1) and stable identities.

#### Verify Pods, PVs, and PVCs
```
NAME            READY   STATUS    RESTARTS   AGE
demo-ss-0   1/1     Running   0          64s
demo-ss-1   1/1     Running   0          60s

NAME                    CAPACITY   ACCESS MODES   RECLAIM POLICY   STATUS      CLAIM                            STORAGECLASS    VOLUMEATTRIBUTESCLASS   REASON   AGE
ss-0   128Mi      RWO            Retain           Bound       default/local-volume-demo-ss-1   local-storage   <unset>                          84s
ss-1   128Mi      RWO            Retain           Available                                    local-storage   <unset>                          84s
ss-2   128Mi      RWO            Retain           Bound       default/local-volume-demo-ss-0   local-storage   <unset>                          84s

NAME                                           STATUS   VOLUME   CAPACITY   ACCESS MODES   STORAGECLASS    VOLUMEATTRIBUTESCLASS   AGE
local-volume-demo-ss-0   Bound    ss-2     128Mi      RWO            local-storage   <unset>                 64s
local-volume-demo-ss-1   Bound    ss-0     128Mi      RWO            local-storage   <unset>                 60s
```
Using ```kubectl get pods,pv,pvc``` shows how each Pod is bound to a specific PVC and PV. Even though three PVs exist, only two are bound because the StatefulSet has two replicas. This output demonstrates the one-to-one relationship between StatefulSet Pods and their Persistent Volumes.

#### Observe stable Pod identity
The pod is created exactly with the same name:
```
kubectl delete pod demo-ss-0
```
Deleting *demo-ss-0* causes Kubernetes to recreate a Pod with the exact same name. StatefulSets preserve Pod identity, which is critical for stateful workloads that depend on stable hostnames and storage mappings.

#### Write data to Pod-specific storage
```
kubectl exec -it demo-ss-0 -- sh
echo "Hello from demo-ss-0" > /mnt/local/hello.txt
```
Writing hello.txt inside demo-ss-0 stores data in that Pod’s dedicated Persistent Volume. This confirms that each StatefulSet Pod has its own isolated storage rather than sharing a single volume.

#### Verify storage isolation between Pods
```
kubectl exec -it demo-ss-1 -- sh
cat /mnt/local/hello.txt // No such file or directory:
```
Accessing the same file path from demo-ss-1 fails because it is backed by a different Persistent Volume. This demonstrates that **StatefulSets provide per-Pod storage isolation**, even when Pods belong to the same application.

#### Confirm persistence across Pod recreation
```
kubectl delete pod demo-ss-0
kubectl exec -it demo-ss-0 -- sh
cat /mnt/local/hello.txt
```
After deleting and recreating demo-ss-0, the file remains accessible because the Persistent Volume Claim was preserved. This shows how StatefulSets decouple data from Pod lifecycles while maintaining consistent identity and storage.

### Dynamically Provisioned Persistent Volumes

#### Identify default StorageClass for dynamic provisioning
Running ```kubectl get storageclass``` identifies the default StorageClass used by the cluster for dynamic volume provisioning. This class defines how storage is automatically created when a PVC is requested.

#### Use volumeClaimTemplates for dynamic provisioning
```
volumeClaimTemplates:
- metadata:
    name: local-volume
    spec:
    accessModes:
        - ReadWriteOnce
    storageClassName: standard 
    resources:
        requests:
        storage: 128Mi
    volumeMode: Filesystem
```
Defining **volumeClaimTemplates with a default StorageClass** allows Kubernetes to dynamically create Persistent Volumes for each StatefulSet Pod. Storage is provisioned automatically without pre-creating PVs, simplifying operational overhead.

#### Create StatefulSet with dynamically provisioned volumes
```
kubectl apply -f ss-statefulset-dynamic.yaml
```
Applying ss-statefulset-dynamic.yaml creates a StatefulSet where each Pod triggers the automatic creation of its own PV. This demonstrates dynamic provisioning in action, with Kubernetes handling storage lifecycle transparently.

#### Verify dynamically created volumes on the node
```
minikube ssh
ls /tmp/hostpath-provisioner/default/
# local-volume-demo-ss-dynamic-0  local-volume-demo-ss-dynamic-1
```
Inspecting the Minikube node filesystem shows directories created by the hostpath provisioner for each Pod. This confirms that dynamic provisioning created backing storage automatically and mapped it to StatefulSet Pods.

#### Cleanup Resources
```
kubectl delete -f ss-statefulset-static.yaml -f ss-persistent-volumes.yaml -f ss-statefulset-dynamic.yaml
# kubectl delete pvc --all
```
Deleting the StatefulSet and related resources removes the Pods and Kubernetes objects. Depending on the reclaim policy, dynamically provisioned volumes may also be cleaned up automatically, completing the lifecycle demonstration.

## Headless Service
A Headless Service in Kubernetes is a Service created with ***clusterIP: None***, which disables virtual IP allocation and load balancing. Instead of routing traffic through a single stable ClusterIP, Kubernetes returns the individual Pod IP addresses directly via DNS. This allows clients to discover and communicate with each Pod instance explicitly rather than through a load-balanced endpoint.

Headless Services are commonly used with StatefulSets and other stateful or peer-to-peer systems such as databases, message brokers, and distributed caches. They enable stable DNS records like ***pod-name.service-name.namespace.svc.cluster.local***, allowing applications to form clusters, perform leader election, or replicate data with full control over which Pod they connect to.

### Example
#### Create the headless Service and StatefulSet
```
kubectl apply -f headless-service.yaml -f statefulset-with-headless-service.yaml
```
Applying headless-service.yaml and statefulset-with-headless-service.yaml creates a headless Service (clusterIP: None) and a StatefulSet that uses it. The headless Service disables load balancing and instead enables **direct Pod discovery**, while the StatefulSet creates Pods with stable names that can be resolved individually through DNS.

#### Inspect the headless Service endpoints
```
kubectl describe svc color-headless-svc
```
- Endpoints: 10.244.0.194:80,10.244.0.192:80,10.244.0.193:80

Describing the Service shows a list of Pod IPs under the Endpoints section rather than a single ClusterIP. This confirms that the Service is headless and that DNS will resolve to individual Pod addresses, allowing clients to connect directly to specific Pods.

#### Create a debug Pod
```
kubectl apply -f pod-with-alpine-image.yaml
```
Applying pod-with-alpine-image.yaml creates a lightweight Alpine-based Pod used for testing connectivity inside the cluster. This Pod serves as a client to validate DNS resolution and direct Pod access provided by the headless Service.

#### Exec into the debug Pod and install curl
```
kubectl exec -it debug-pod -- sh
apk --update add curl
```
Entering the debug Pod and installing curl allows you to make HTTP requests from within the cluster network. This ensures that service discovery and networking behavior are tested in the same environment where applications normally run.

#### Access individual Pods via DNS
```
curl color-ss-0.color-headless-svc.default.svc.cluster.local
curl color-ss-1.color-headless-svc.default.svc.cluster.local
```

Curling *color-ss-0.color-headless-svc.default.svc.cluster.local* and *color-ss-1.color-headless-svc.default.svc.cluster.local* demonstrates stable, per-Pod DNS resolution. Each hostname maps to a specific Pod, confirming how headless Services enable direct, predictable communication with StatefulSet replicas.

#### Cleanup Resources
```
kubectl delete -f pod-with-alpine-image.yaml -f headless-service.yaml -f statefulset-with-headless-service.yaml
kubectl delete pvc --all
```
Deleting the debug Pod, headless Service, StatefulSet, and associated PVCs removes all created resources and storage. This final step ensures the cluster is returned to a clean state after the demonstration.
