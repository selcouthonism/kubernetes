# Kubernetes API
The Kubernetes API is the central control interface of a Kubernetes cluster. Every action in Kubernetes (creating Pods, scaling Deployments, fetching logs, or executing a command inside a container) ultimately becomes an HTTP request to the Kubernetes API server. Kubernetes is fundamentally an API-driven system, and all tools (including kubectl, controllers, operators, and dashboards) interact with the cluster through this API.

## Kubernetes API Overview
The Kubernetes API is exposed by the kube-apiserver, which:
- Validates and processes API requests
- Performs authentication and authorization
- Persists desired state into etcd
- Acts as the single entry point to the control plane

Resources in Kubernetes are represented as RESTful objects (Pods, Services, Deployments, etc.), and each object is accessed via a versioned API endpoint.

### Core API Group
The Core API Group (also called the legacy API group) contains the most fundamental Kubernetes resources and is accessed under ```/api/v1```. Key resources in the Core API group include: Pods, Services, ConfigMaps, Secrets, PersistentVolumes / PersistentVolumeClaims, Namespaces, Nodes, ServiceAccounts, Events. These resources do not have an explicit API group name; they are simply versioned as v1.

### Named API Groups
As Kubernetes evolved, additional functionality was organized into named API groups to improve extensibility and versioning. These APIs are accessed under ```/apis/<group>/<version>```.

Named API groups include:
- **apps/v1** – Deployments, StatefulSets, DaemonSets, ReplicaSets
- **batch/v1** – Jobs, CronJobs
- **autoscaling/v1,v2** – HorizontalPodAutoscaler
- **networking.k8s.io/v1** – NetworkPolicies, Ingress, IngressClass
- **discovery.k8s.io/v1** – EndpointSlice
- **rbac.authorization.k8s.io/v1** – Roles, RoleBindings, ClusterRoles
- **authentication.k8s.io/v1** – TokenReview
- **authorization.k8s.io/v1** – SubjectAccessReview, SelfSubjectAccessReview
- **policy/v1** – PodDisruptionBudgets
- **storage.k8s.io/v1** – StorageClasses, CSIDrivers
- **coordination.k8s.io/v1** – Lease
- **admissionregistration.k8s.io/v1** – MutatingWebhookConfiguration, ValidatingWebhookConfiguration
- **apiextensions.k8s.io/v1** – CustomResourceDefinition (CRD)
- **apiregistration.k8s.io/v1** – APIService
- **acertificates.k8s.io/v1** – CertificateSigningRequest
- **events.k8s.io/v1** – Event
- **node.k8s.io/v1** – RuntimeClass
- **scheduling.k8s.io/v1** – PriorityClass

Named API groups allow independent evolution and clearer ownership of features.

kubectl is just a client for the Kubernetes API. It does not perform operations directly.

kubectl:
1. Reads cluster credentials from kubeconfig
2. Authenticates to the API server
3. Translates commands into REST API calls
4. Sends HTTP requests to the API server
5. Displays the API server’s response

kubectl get pods                 : GET /api/v1/namespaces/default/pods
kubectl apply -f deployment.yaml : POST/PATCH /apis/apps/v1/namespaces/default/deployments

### Subresources in Kubernetes
Subresources are special API endpoints that represent operations or partial views of a resource rather than the full object. They allow fine-grained access control and safer updates.

#### Pod Subresources
- **logs**: Used to fetch container logs
    - kubectl: ```kubectl logs my-pod``` 
    - api: ```GET /api/v1/namespaces/{ns}/pods/{pod}/log```

- **exec**: Used to execute a command inside a container
    - kubectl: ```kubectl exec -it my-pod -- sh```
    - api: ```POST /api/v1/namespaces/{ns}/pods/{pod}/exec```

- **attach**: Used to attach to a running container’s stdin/stdout
    - kubectl: ```kubectl attach my-pod```
    - api: ```POST /api/v1/namespaces/{ns}/pods/{pod}/attach```

#### Deployment Subresources
- **scale**: Used to change the replica count without modifying the entire object
    - kubectl: ```kubectl scale deployment my-app --replicas=5``` 
    - api: ```/apis/apps/v1/namespaces/{ns}/deployments/{name}/scale```

- **status**: Used to update or read runtime status (conditions, available replicas). Controllers update status, while users typically read it.
    - api: ```/apis/apps/v1/namespaces/{ns}/deployments/{name}/status```

### RBAC Controls API Access
RBAC operates directly on API requests, including subresources.

RBAC Rule Structure
RBAC rules specify:
- apiGroups – which API group
- resources – which resource
- verbs – allowed actions
- resourceNames (optional)
- subresources (implicit via resource syntax)

Subresources are treated as separate RBAC resources.

Examples:
- pods/log → access to logs
- pods/exec → exec into containers
- pods/attach → attach to containers
- deployments/scale → scale deployments
- deployments/status → read/update status

Role-Based Access Control (RBAC) governs all of these interactions by authorizing requests at the API level, including subresources, allowing fine-grained permission models such as letting a user read pod logs but not exec into containers, or scale deployments without editing their specs, thereby enforcing least privilege and strengthening cluster security.

Example RBAC rule allowing log access but not exec:
```
rules:
- apiGroups: [""]
  resources: ["pods/log"]
  verbs: ["get"]
```

Example rule allowing scaling but not editing deployments:
```
rules:
- apiGroups: ["apps"]
  resources: ["deployments/scale"]
  verbs: ["update"]
```
