# Kubernetes Security
Kubernetes security is built on multiple, layered controls that protect the cluster, workloads, data, and supply chain. Rather than relying on a single mechanism, Kubernetes follows a defense-in-depth approach where access control, network isolation, data protection, workload hardening, and image trust work together.

Kubernetes security is a layered system:
- RBAC secures API access
- Network Policies control traffic flow
- Encryption at Rest protects stored secrets
- Pod Security Standards harden workloads
- Image Security secures the software supply chain

Together, these mechanisms reduce attack surfaces, limit blast radius, and enforce secure-by-default workloads in production Kubernetes environments.

### RBAC (Role-Based Access Control)
RBAC controls who can do what in a Kubernetes cluster by regulating access to the Kubernetes API. Permissions are defined using ***Roles*** and ***ClusterRoles***, which specify allowed actions (verbs like **get**, **list**, **create**, **delete**) on resources (pods, secrets, deployments). These roles are assigned to **users**, **groups**, or **service accounts** using ***RoleBindings*** or ***ClusterRoleBindings***. RBAC enforces the principle of least privilege, ensuring that humans and applications only have the minimum permissions they need, reducing the blast radius of compromised credentials.

### Network Policies
Network Policies define how Pods are allowed to communicate with each other and with external services at the network layer. By default, Kubernetes allows all Pod-to-Pod communication, but Network Policies enable you to restrict traffic based on Pod labels, namespaces, IP ranges, and ports. This creates microsegmentation inside the cluster, preventing lateral movement if a Pod is compromised and ensuring that only explicitly allowed traffic paths are permitted.

### Encryption at Rest
Encryption at rest protects **sensitive data stored in etcd**, such as Secrets and ConfigMaps, from being read in plaintext if the underlying storage is compromised. Kubernetes supports encryption at rest using an **encryption provider configuration**, which can integrate with systems like AWS KMS, Azure Key Vault, GCP KMS, or HashiCorp Vault. While Kubernetes Secrets are Base64-encoded by default, enabling encryption at rest ensures they are cryptographically protected on disk, strengthening compliance and security posture.

### Pod Security Standards (PSS)
Pod Security Standards define baseline security requirements for Pods to prevent dangerous configurations. Kubernetes provides three standard profiles: **Privileged**, **Baseline**, and **Restricted**. These standards control settings such as running containers as root, privilege escalation, use of host networking, and access to host filesystems. Enforcing PSS at the namespace level ensures workloads follow consistent security rules and reduces the risk of container breakout or node compromise.

### Image Security
Image security focuses on ensuring that only trusted and safe container images run in the cluster. This includes scanning images for vulnerabilities, using minimal base images, pinning image versions (avoiding latest), and signing images to verify authenticity. Admission controllers or policy engines (like OPA Gatekeeper or Kyverno) can block untrusted images, enforce registry allowlists, and require vulnerability scan results before deployment. Strong image security protects the cluster from supply chain attacks and known CVEs.
