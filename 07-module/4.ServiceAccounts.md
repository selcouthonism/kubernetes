# Service Accounts
ServiceAccounts are Kubernetes identities designed specifically for workloads running inside the cluster, not for humans. When a Pod needs to talk to the Kubernetes API (for example, to list Pods, watch ConfigMaps, or update a custom resource), it authenticates as a ServiceAccount. Kubernetes automatically creates a ServiceAccount named **default** in every namespace, and unless specified otherwise, every Pod runs using this default ServiceAccount. Unlike user accounts, ServiceAccounts are **managed by Kubernetes itself** and are tightly integrated with RBAC, making them the standard way to grant permissions to applications.

A ServiceAccount is associated with a credential, historically a Secret containing a token, and in modern Kubernetes versions via projected ServiceAccount tokens that are short-lived, automatically rotated, and scoped. When a Pod is created, Kubernetes injects the ServiceAccount token and cluster CA certificate into the Pod (typically under ```/var/run/secrets/kubernetes.io/serviceaccount```). Client libraries inside the container use this token to authenticate requests to the API server. The API server identifies the caller as ```system:serviceaccount:<namespace>:<serviceaccount-name>``` and uses this identity during authorization.

ServiceAccounts are authorized using RBAC, just like users. You grant permissions by binding Roles or ClusterRoles to a ServiceAccount using RoleBindings or ClusterRoleBindings. For example, binding a Role that allows get and list on Pods enables a Pod running with that ServiceAccount to read Pod information, while all other actions remain forbidden. This enables least-privilege access, ensuring that applications have only the permissions they truly need.

ServiceAccounts also play a key role beyond API access. They are commonly used to **access external systems** (for example, cloud services via workload identity), to pull images from private registries (via imagePullSecrets), and to isolate permissions between different applications in the same namespace. Best practice is to **create one ServiceAccount per application**, disable API token mounting when not needed (**automountServiceAccountToken: false**), and avoid using the default ServiceAccount for anything beyond trivial workloads.

### Default ServiceAccount per namespace:
Every namespace gets its own serviceaccount:
```
kubectl get serviceaccounts
kubectl describe serviceaccounts default

kubectl get serviceaccounts -n dev
kubectl describe serviceaccounts default -n dev
```
Kubernetes automatically creates a **default** ServiceAccount in every namespace, which is why running ```kubectl get serviceaccounts``` and ```kubectl get serviceaccounts -n dev``` shows a default entry in both namespaces. By describing it, you can see that this ServiceAccount exists even if you never explicitly created one. When a Pod does not specify a ServiceAccount, **Kubernetes implicitly assigns the namespace’s default ServiceAccount to that Pod**, which means workloads always have an identity unless you explicitly disable it.

### Listing ServiceAccounts across the cluster:
Using ```kubectl get sa -A``` lists ServiceAccounts in all namespaces, reinforcing the idea that ServiceAccounts are namespaced resources. This scoping is critical for security because a ServiceAccount in one namespace cannot automatically act in another namespace, even if it has the same name, ensuring isolation between environments like *dev* and *prod*.

### Creating custom ServiceAccounts
```
kubectl apply -f serviceaccount-pod-inspector.yaml -f serviceaccount-pod-inspector-ns-dev.yaml 
```
Applying *serviceaccount-pod-inspector.yaml* and *serviceaccount-pod-inspector-ns-dev.yaml* creates custom ServiceAccounts, one likely cluster-wide or default-namespaced and one specifically in the *dev* namespace. This step demonstrates best practice: instead of relying on the default ServiceAccount, you create a dedicated ServiceAccount that represents a specific application or responsibility, making permission management explicit and auditable.

#### Running a Pod with a specific ServiceAccount
```
kubectl apply -f pod-alpine-ns-dev.yaml
```
When you apply *pod-alpine-ns-dev.yaml*, the Pod is created in the *dev* namespace and explicitly configured to use the *pod-inspector* ServiceAccount. Describing the Pod confirms this with *Service Account: pod-inspector*, showing how Pods can be bound to a non-default identity, which is essential for fine-grained RBAC control.

```
kubectl describe pod alpine-curl-pod -n dev
# Service Account:  pod-inspector
```

#### Inspecting the ServiceAccount token inside the Pod
```
kubectl exec -it alpine-curl-pod -n dev -- sh
cat /var/run/secrets/kubernetes.io/serviceaccount/token
```
By exec’ing into the Pod and reading ```/var/run/secrets/kubernetes.io/serviceaccount/token```, you can see the actual bearer token mounted by Kubernetes. This demonstrates how authentication works internally: Kubernetes injects the **ServiceAccount token** and **CA certificate** into the container so that in-cluster applications can securely authenticate to the API server without embedding credentials in images.

#### Using the ServiceAccount token to call the Kubernetes API:
```
TOKEN=$(cat /var/run/secrets/kubernetes.io/serviceaccount/token)

curl -s --header "Authorization: Bearer $TOKEN" --cacert /var/run/secrets/kubernetes.io/serviceaccount/ca.crt https://kubernetes.default.svc/api/v1/namespaces/dev/pods
```
Exporting the token and using curl against ```https://kubernetes.default.svc``` shows a real API call authenticated as the ServiceAccount. At this stage, the request typically fails or is limited because authentication alone is not enough—authorization via RBAC is still required. This clearly separates **authentication (who you are)** from **authorization (what you can do)**.

#### Granting permissions via RoleBinding
Update rolebinding-pod-reader-ns-dev.yaml with:
```
- kind: ServiceAccount
  name: pod-inspector
  namespace: dev
```
Updating *rolebinding-pod-reader-ns-dev.yaml* to include the *pod-inspector ServiceAccount* binds an existing Role to this ServiceAccount in the *dev* namespace. Once applied, Kubernetes authorizes API requests made with this ServiceAccount token according to the Role’s rules, enabling actions like get and list Pods while still denying anything outside the defined scope.
```
kubectl apply -f rolebinding-pod-reader-ns-dev.yaml
```

#### Verifying RoleBinding configuration:
```
kubectl describe rolebinding pod-reader -n dev
```
Describing the RoleBinding confirms that the subject now includes the *ServiceAccount pod-inspector* in the *dev* namespace. This step is important for debugging RBAC, as it lets you verify exactly which identities (users, groups, or ServiceAccounts) are bound to which roles and in which namespace.

### CleanUp Resources:

#### Cleaning up namespaces and resources:
```
kubectl delete ns dev
kubectl delete ns prod
```

Deleting namespaces such as *dev* and *prod* is the fastest cleanup method because namespaces are resource boundaries—removing them automatically deletes all contained Pods, Services, Roles, RoleBindings, and ServiceAccounts.

```
kubectl delete -f roles/pod-nginx-ns-dev.yaml -f roles/pod-nginx-ns-prod.yaml -f roles/role-pod-reader-ns-dev.yaml -f roles/rolebinding-pod-reader-ns-dev.yaml -f roles/clusterrole-pod-admin.yaml -f roles/clusterrolebinding-pod-admin.yaml -f serviceaccounts/pod-alpine-ns-dev.yaml -f serviceaccounts/serviceaccount-pod-inspector-ns-dev.yaml -f serviceaccounts/serviceaccount-pod-inspector.yaml -f roles/ns-dev.yaml -f roles/ns-prod.yaml -f credentials/csr.yaml
```
Alternatively, deleting resources one by one demonstrates how granular cleanup works and reinforces the relationship between RBAC objects, ServiceAccounts, and workloads.

#### Cleaning kubeconfig user and context entries:
```
kubectl config view
kubectl config delete-context bob-context alice-context
kubectl config delete-user bob alice
```
Finally, removing contexts and users from the kubeconfig ensures that locally generated credentials (like alice and bob) are fully cleaned up. This step prevents stale identities from lingering in your client configuration and reinforces good hygiene when experimenting with authentication, authorization, and ServiceAccounts in Kubernetes.
