Role-Based Access Control (RBAC) in Kubernetes is the authorization mechanism that determines who can perform which actions on which resources. It protects the Kubernetes API by ensuring users, applications, and services only have the permissions they actually need, following the principle of least privilege.

## Core RBAC Components
### 1. Subject
A Subject represents who is requesting access. In Kubernetes, subjects can be:
- **User** – a human user authenticated by an external identity provider
- **Group** – a collection of users (for example, dev-team)
- **ServiceAccount** – an identity used by Pods and controllers inside the cluster

Subjects themselves do not have permissions; they must be bound to roles.

### 2. Role
A Role defines what actions are allowed within a specific namespace. It contains rules that specify:
- **Resources** (pods, services, secrets, configmaps, etc.)
- **Verbs** (get, list, watch, create, update, delete)
- Optionally **API groups** and **resource names**

Roles are namespace-scoped, meaning they only apply to resources in a single namespace.

### 3. ClusterRole
A ClusterRole is similar to a Role but applies cluster-wide. It is used when:
- Access is needed across all namespaces
- Permissions are required for cluster-scoped resources (nodes, persistentvolumes)
- Reusable roles are needed for multiple namespaces

Kubernetes ships with many built-in ClusterRoles such as **view**, **edit**, and **admin**.

### 4. RoleBinding
A RoleBinding connects a Role or ClusterRole to one or more Subjects within a namespace. It answers the question: *Who gets this role in this namespace?*

Important points:
- A RoleBinding is namespace-scoped
- It can reference either a Role (namespace-scoped) or a ClusterRole
- Permissions only apply within the RoleBinding’s namespace

### 5. ClusterRoleBinding
A ClusterRoleBinding grants a ClusterRole to Subjects across the entire cluster.

It is used for:
- Cluster administrators
- System components
- Read-only access across all namespaces

Once bound, the permissions apply everywhere in the cluster.

### Summary
Role and RoleBinding are **namespace-scoped**, meaning the permissions they grant are limited to a single, specified namespace.

ClusterRole and ClusterRoleBinding are **cluster-scoped** (or global), meaning the permissions they grant apply across all namespaces in the cluster, or to cluster-level resources like nodes.

## Role and RoleBinding manifest
### Role Manifest
```
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: dev
rules:
- apiGroups: [""] # "" indicates the core API group (rbac.authorization.k8s.io/v1)
  resources: ["pods"]
  verbs: ["get", "list"]
```
This manifest defines a Role, which is a fundamental component of Kubernetes RBAC (Role-Based Access Control).

You should notice that this is a namespaced resource. Unlike a **ClusterRole**, which applies to the entire cluster, this Role is strictly confined to the boundaries of the *dev* namespace.

#### 1. Scope and Identification
**apiVersion: rbac.authorization.k8s.io/v1**: This belongs to the RBAC API group, which is the standard for authorization in modern Kubernetes clusters.

**kind: Role**: This specifies that the permissions defined here are local to a namespace.

**metadata**:
- **name: pod-reader**: The name you'll use to reference this role later.

- **namespace: dev**: This is critical. This role can **only** grant access to pods inside the *dev* namespace. It cannot see pods in production, default, or any other namespace.

#### 2. Defining the Rules (The "Policy")
The **rules** section is where you define exactly what is allowed. Kubernetes RBAC is additive (allow-only); there are no "deny" rules. If it’s not explicitly listed here, it’s forbidden.

**apiGroups: [""]**: The empty string is shorthand for the Core API Group. This is where basic objects like Pods, Services, and ConfigMaps live. If you were defining permissions for a Deployment, you would use ["apps"].

apiGroups in Kubernetes RBAC refer to logical groupings of related API resources. Think of them as categories for different kinds of objects you can manage in Kubernetes. For example, core resources like pods and services are in the "" (empty string) core API group, while deployments and replicasets are in the apps API group.

They are essential because they allow you to define very granular permissions. Instead of granting access to all resources, you can specify that a user can only interact with resources belonging to a particular API group. This helps prevent over-privileging users and enhances security.

**resources: ["pods"]**: This specifies the type of object the rule applies to.

**verbs: ["get", "list"]**: These are the allowed actions.

- **get**: Retrieve the details of a single, specific pod (if you know its name).
- **list**: Retrieve a list of all pods in the namespace.

Note that watch, create, update, patch, and delete are missing. This makes it a "read-only" role.

It is important to remember that applying this YAML does nothing on its own. A ***Role*** is just a template of permissions. To actually give a user, group, or ServiceAccount these powers, you must create a ***RoleBinding***.

Think of it this way:
- **Role**: The "Job Description" (What can be done).
- **User/ServiceAccount**: The "Person" (Who is doing it).
- **RoleBinding**: The "Contract" (Connecting the person to the job).

#### Tip: The Principle of Least Privilege
When designing RBAC, always start with a ***Role*** rather than a ***ClusterRole***. By scoping permissions to a specific namespace like dev, you ensure that a compromised ServiceAccount or a developer mistake in a test environment cannot accidentally delete or modify production workloads.

### RoleBinding Manifest
```
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: pod-reader-binding
  namespace: dev # must match the Role's namespace
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: pod-reader
subjects:
- kind: User
  name: bob
  apiGroup: rbac.authorization.k8s.io
```
If the Role is a "job description," then the RoleBinding is the "employment contract." It is the bridge that officially connects a set of permissions to a specific person or service.

You should view a ***RoleBinding*** as the point where security policy meets identity management.

#### 1. The Metadata (The Context)
**kind: RoleBinding**: This resource grants permissions within a specific namespace.

**namespace: dev**: This must match the namespace of the Role you are referencing. In Kubernetes RBAC, you cannot use a RoleBinding in the dev namespace to grant a Role that exists in the prod namespace. They must be co-located.

#### 2. The roleRef (The "What")
The roleRef section points to the permissions you want to grant.

**kind: Role**: Tells Kubernetes to look for a namespaced Role (rather than a cluster-wide ClusterRole).

**name: pod-reader**: This must exactly match the metadata.name of the Role manifest we discussed previously.

**apiGroup**: Specifies the RBAC API.

**Crucial Tip:** The ***roleRef*** field is immutable. Once you create a RoleBinding, you cannot change which Role it points to. If you want to change the permissions from pod-reader to pod-admin, you must delete the RoleBinding and create a new one.

#### 3. The subjects (The "Who")
The subjects list defines the entities that will receive these permissions. You can bind a role to multiple subjects at once.

**kind: User**: This represents a human actor. In this case, the user named "bob".

**apiGroup**: For Users and Groups, this is always rbac.authorization.k8s.io.

##### Note on Users vs. ServiceAccounts:
- A User is usually managed outside of Kubernetes (like through Google Workspace, LDAP, or certificates).
- If you wanted to give these permissions to a bot or a pod, you would change kind to ***ServiceAccount***.

#### Practical Workflow
When bob tries to run ```kubectl get pods -n dev```, the Kubernetes API server performs the following check:
1. Is there a **RoleBinding** in the *dev* namespace that includes bob as a subject?
2. Does that binding point to a **Role**?
3. Does that Role allow the "get" verb on the "pods" resource?
4. If all are "Yes," the request is allowed.

The logic we just discussed is local to the *dev* namespace. However, sometimes you need a user to have "Global" powers (like viewing nodes across the whole cluster). In that case, you would use a ***ClusterRole*** and a ***ClusterRoleBinding***.

> Note: Troubleshoot RBAC issues using the ```kubectl auth can-i```

### ClusterRole Manifest
```
kind: ClusterRole
metadata:
  name: pod-admin
rules:
- apiGroups: [""] # "" indicates the core API group
  resources: ["pods", "pods/log", "pods/exec", "pods/attach"]
  verbs: ["*"] # "*" means all verbs
```

While a ***Role*** is restricted to a single namespace, a ***ClusterRole*** is a cluster-wide resource. You use ClusterRoles for two main purposes:

- Defining permissions for non-namespaced resources (like Nodes, PersistentVolumes, or Namespaces).
- Defining a "Global Template" of permissions that can be applied to any namespace in the cluster.

Here is the breakdown of the pod-admin manifest.

#### 1. Scope: The Global Authority
**kind: ClusterRole**: Unlike the previous Role, this object does not have a namespace field in its metadata. It exists at the top level of the cluster.

**metadata.name: pod-admin**: This name is now reserved globally. You cannot have two ClusterRoles with the same name.

#### 2. Resources and Subresources
This is where this manifest becomes very powerful. Notice the distinction in the resources list:

**pods**: Grants access to the base Pod objects (creating, deleting, etc.).

**pods/log**: This is a subresource. Having permission for pods does not automatically grant the ability to read logs. You must explicitly list pods/log.

**pods/exec** and **pods/attach**: These are the "keys to the kingdom." They allow a user to open a shell inside a running container. In a production environment, these are usually restricted to senior engineers or emergency "break-glass" accounts.

#### 3. The Power of the Wildcard (*)
**verbs: ["*"]**: The asterisk is a wildcard. It grants all possible actions—get, list, watch, create, update, patch, and delete.

The "Admin" Designation: Because it combines full verbs with exec and attach capabilities, any user with this role is effectively a "Pod Superuser." They can't delete the whole cluster, but they can manipulate every single workload within the scope of their binding.

#### Tip: Reusable Templates
In large organizations, we rarely create individual Roles for every team. Instead, we create a few standard ClusterRoles (like *pod-admin*) and then use RoleBindings in each team's namespace to grant them those specific permissions. This ensures consistent security policies across the entire company.

### ClusterRoleBinding Manifest
```
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: pod-admin
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: pod-admin
subjects:
- kind: Group
  name: admin
  apiGroup: rbac.authorization.k8s.io
```
The ***ClusterRoleBinding*** is the final piece of the RBAC puzzle that grants cluster-wide authority. While a ***RoleBinding*** limits permissions to a single namespace, a ***ClusterRoleBinding*** applies the permissions of a ***ClusterRole*** to every single namespace in your cluster, plus cluster-scoped resources like Nodes and PVs.

In this specific manifest, we are granting high-level administrative powers to an entire group of people.

#### 1. Scope: Total Coverage
**kind: ClusterRoleBinding**: This resource is not namespaced. It exists at the cluster level and manages access across the entire environment.

**metadata.name: pod-admin**: Like the ClusterRole, this name must be unique across the whole cluster. It is common practice to name the binding similarly to the role it grants for easier auditing.

#### 2. The roleRef (The Authority)
**kind: ClusterRole**: You are referencing a cluster-level role.

**name: pod-admin**: This points to the ClusterRole we discussed previously (the one with * verbs on pods, exec, and logs).

Because this is a ClusterRoleBinding pointing to a ClusterRole, the permissions are active everywhere. If you have 100 namespaces, the subjects of this binding are now admins in all 100.

#### 3. The subjects: Group Management
This is where this manifest differs from our previous bob example:

**kind: Group**: This is a powerful way to manage access at scale. Instead of listing 50 individual users by name, you point to a group named "admin".

In a production-grade cluster, this "admin" group usually maps to an external identity provider (IdP) like Okta, Azure AD, or Google Workspace.

If a new engineer joins the company and is added to the "admin" group in your IdP, they automatically inherit these Kubernetes permissions without you needing to update a single YAML file.

#### Note: The "Superuser" Trap
Be extremely careful with ClusterRoleBindings that use wildcards (*). Because this binding applies to the admin group, if an account in that group is compromised, the attacker has **exec** and **log** access to every pod in your system, including system-critical pods in kube-system.

Always audit these bindings regularly using: ```kubectl get clusterrolebindings```

## RBAC Setup
The following RBAC walkthrough demonstrates the full lifecycle of Kubernetes security: authentication via certificates, identity propagation through kubeconfig, resource discovery via the API, and fine-grained authorization using Roles, ClusterRoles, and bindings. It highlights how Kubernetes treats users as external identities, enforces least privilege by default, and applies RBAC uniformly—even to powerful subresources like exec and logs.

### Explore context, user, and roles in minikube
```
kubectl config view
kubectl config current-context
```

Output:
```
users:
- name: minikube
  user:
    client-certificate: <home_path>/.minikube/profiles/minikube/client.crt
    client-key: <home_path>/.minikube/profiles/minikube/client.key
```
Kubernetes itself does not manage users internally; instead, it relies on external identity mechanisms such as client certificates, OIDC providers (Azure AD, Google, etc.), or authentication proxies. In Minikube, authentication is typically done using client certificates embedded in the kubeconfig file. By running ```kubectl config view``` and ```kubectl config current-context```, you inspect how kubectl authenticates to the API server and which cluster, user, and namespace are active. The users section shows that Minikube uses a certificate and private key, which the API server validates to authenticate the caller. The certificate subject (CN=minikube-user, O=system:masters) is critical because RBAC decisions later depend entirely on this identity information.

### Inspect built-in ClusterRoles and ClusterRoleBindings
```
kubectl get clusterroles
kubectl get clusterroles admin -o yaml
kubectl get clusterroles cluster-admin -o yaml
```
Kubernetes ships with predefined ***ClusterRoles*** such as **admin** and **cluster-admin** to support common access patterns. Using ```kubectl get clusterroles``` and inspecting their YAML definitions shows how permissions are expressed in terms of API groups, resources, and verbs. The **cluster-admin** role is effectively unrestricted and is commonly bound to the *system:masters* group.
```
kubectl get clusterrolebindings
kubectl get clusterrolebindings | grep cluster-admin
kubectl get clusterrolebindings cluster-admin -o yaml
kubectl get clusterrolebindings minikube-rbac -o yaml
```
***ClusterRoleBindings*** connect these roles to users or groups, and by examining bindings like **minikube-rbac**, you can see that the Minikube user is granted full cluster access. This demonstrates how RBAC authorization is entirely declarative and binding-based, with no implicit permissions.

### Inspecting the Minikube user certificate
```
openssl x509 -noout -text -in '<home_path>/.minikube/profiles/minikube/client.crt'
# Subject: O=system:masters, CN=minikube-user
```
By decoding the Minikube client certificate using OpenSSL, you can see that the user belongs to the **system:masters** group. This group is special because it is automatically bound to the **cluster-admin** role in most Kubernetes distributions. The Kubernetes API server extracts the **Common Name (CN)** as the username and the **Organization (O)** fields as group memberships. These values are then matched against ***RoleBindings*** and ***ClusterRoleBindings*** during authorization. This step clearly shows how **certificates directly map to RBAC identities**.

### Generating private keys for Alice and Bob
generate keys for users: alice.key and bob.key are Private keys.
```
openssl --version
openssl genrsa -out alice.key 2048
openssl genrsa -out bob.key 2048
```
To simulate real users, you generate private keys for Alice and Bob using OpenSSL. These private keys act as cryptographic proof of identity and are required to authenticate to the Kubernetes API server. At this stage, the users exist only as key material; Kubernetes is still unaware of them. This mirrors real-world setups where identity originates outside Kubernetes, and access is granted only after explicit authorization.

### Creating certificate signing requests (CSRs)
```
openssl req -new -key alice.key -out alice.csr -subj "/CN=alice/O=admin"
openssl req -new -key bob.key -out bob.csr -subj "/CN=bob/O=dev"
```
```
kubectl apply -f csr.yaml
```
```
kubectl get csr
kubectl get certificatesigningrequest
```

Output:
```
NAME       AGE  SIGNERNAME                           REQUESTOR      REQUESTEDDURATION  CONDITION
alice-csr  87s  kubernetes.io/kube-apiserver-client  minikube-user  24h                Pending
bob-csr    87s  kubernetes.io/kube-apiserver-client  minikube-user  24h                Pending
```
The CSR step introduces the user identity into Kubernetes by embedding the desired username (CN) and group (O) into the request. For example, Alice is placed in the *admin* group, while Bob is placed in the *dev* group. These attributes become immutable identity claims once the certificate is issued. Kubernetes does not validate whether these groups exist; it only verifies signatures and later checks RBAC bindings. This separation of **authentication (who you are)** and **authorization (what you can do)** is a core Kubernetes security principle.

### Signing CSRs using the Kubernetes CA
```
kubectl certificate approve alice-csr bob-csr
```
When the CSRs are submitted to Kubernetes, they appear as ***CertificateSigningRequest*** objects that must be explicitly approved. This approval step acts as a gatekeeper, ensuring that only trusted identities receive valid client certificates. Once approved, the Kubernetes CA signs the certificates, making them trusted by the API server. From this point forward, Alice and Bob can authenticate successfully, but they still have zero permissions until RBAC rules are applied.

### Extracting and validating issued certificates
```
kubectl get csr alice-csr -o jsonpath='{.status.certificate}' | base64 -d > alice.crt

kubectl get csr bob-csr -o jsonpath='{.status.certificate}' | base64 -d > bob.crt

cat alice.crt bob.crt
```

```
openssl x509 -noout -text -in 'alice.crt'
# Subject: O=admin, CN=alice

openssl x509 -noout -text -in 'bob.crt'
# Subject: O=dev, CN=bob
```
After approval, the signed certificates are extracted and validated using OpenSSL. This confirms that the certificates contain the expected subject information, including usernames and group memberships. Kubernetes does not store users as objects; instead, every API request carries identity information derived from the certificate. This reinforces the idea that **RBAC decisions are evaluated dynamically on every request**.

### Adding users and contexts to kubeconfig
Look at the default location:
```
cat ~/.kube/config
```

Override the default kube config file via ```export KUBECONFIG="<path>"```. In this exmaple, we use default kube config file.

Addding context to kube config file:
```
kubectl config set-context alice-context --cluster minikube --user alice
kubectl config set-context bob-context --cluster minikube --user bob
```
You can delete the context via ```kubectl config delete-context alice-context```

Adding user to kube config file:
```
kubectl config set-credentials alice --client-key $(realpath alice.key) --client-certificate $(realpath alice.crt)

kubectl config set-credentials bob --client-key $(realpath bob.key) --client-certificate $(realpath bob.crt)
```
**--embed-certs=true**: Not mentions the files but add the base64 of key and crt into the kube config file directly.

You can delete user via ```kubectl config delete-user alice```

By adding credentials and contexts to the kubeconfig file, you enable kubectl to authenticate as Alice or Bob. A context ties together a cluster, a user, and a namespace, making it easy to switch identities without changing credentials manually. Embedding certificates directly into the kubeconfig simplifies portability but does not change the security model. At this point, Alice and Bob can authenticate, but authorization is still enforced by RBAC.

View configuration via ```kubectl config view```

### Observing authorization failure without RBAC permissions
Switch context from minikube to alice-context:
```
kubectl config use-context alice-context
kubectl config current-context
```

```
kubectl get pods
```
When Alice attempts to list pods and receives a “Forbidden” error (*Error from server (Forbidden): pods is forbidden: User "alice" cannot list resource "pods" in API group "" in the namespace "default"*), it demonstrates that authentication alone is insufficient. The Kubernetes API server authenticates the request successfully but denies it during authorization because no Role or ClusterRole grants the required permissions. This is the default secure posture of Kubernetes: **deny by default unless explicitly allowed**.

### Discovering available API resources
List all resources available in the cluster:
```
kubectl api-resources
kubectl api-resources --namespaced=true
kubectl api-resources --api-group=storage.k8s.io
kubectl api-resources --api-group=storage.k8s.io -o wide

Using ```kubectl api-resources```, you inspect which resources exist, whether they are namespaced, and which API groups they belong to. For example, pods belong to the core API group (""), while storage resources live under storage.k8s.io. RBAC rules that reference incorrect API groups simply do not match, resulting in denied access.

### Creating namespaces and deploying workloads
Make sure the current context is minikube. Alice and Bob does not have a permission.
```
kubectl config use-context minikube
kubectl config current-context
```

```
kubectl apply -f ns-dev.yaml -f ns-prod.yaml -f pod-nginx-ns-dev.yaml -f pod-nginx-ns-prod.yaml 
```
By creating *dev* and *prod* namespaces and deploying nginx pods into each, you establish isolated scopes for authorization. Namespaces are a fundamental boundary in Kubernetes RBAC, allowing the same role name to exist with different permissions in different namespaces. This setup prepares the environment to demonstrate fine-grained, namespace-scoped access control.

```
kubectl get pods -A | grep nginx
```

### Granting Bob read-only access to pods in the dev namespace
```
kubectl apply -f role-pod-reader-ns-dev.yaml -f rolebinding-pod-reader-ns-dev.yaml
```
A ***Role*** is created to allow **get** and **list** access to pods within the *dev* namespace, and a ***RoleBinding*** connects this Role to Bob. This limits Bob’s visibility strictly to pods in *dev* and prevents access to other namespaces or cluster-wide resources. When Bob switches context, he can successfully list and describe pods in *dev*, but all other actions remain forbidden. This shows how Roles are namespace-scoped and least-privilege by design.

```
kubectl get roles,rolebinding -n dev
```

Switch context to bob-context:
```
kubectl config use-context bob-context

Error from server (Forbidden):

### Creating a ClusterRole for pod administration
Make sure the current context is minikube.
```
kubectl config use-context minikube
kubectl config current-context
```

Create a cluster role and clusterrolebinding for Group admin:
```
kubectl apply -f clusterrole-pod-admin.yaml
```
The *pod-admin* ClusterRole grants full access to pods and their subresources such as logs, exec, and attach across the entire cluster. Subresources are treated as distinct RBAC resources, meaning access to pods alone does not automatically allow access to **pods/log** or **pods/exec**. This design prevents privilege escalation and allows extremely fine-grained control over sensitive operations like remote command execution.

### Binding the ClusterRole to the admin group
```
kubectl apply -f clusterrolebinding-pod-admin.yaml
```
By creating a ClusterRoleBinding that associates the *pod-admin* role with the *admin* group, all users whose certificates include **O=admin** gain these elevated privileges. Alice, as a member of this group, can now create, delete, exec into, and retrieve logs from pods in any namespace. Bob, who is not part of the group, remains restricted. This clearly illustrates group-based RBAC and how it scales better than user-specific bindings.

```
kubectl get clusterrole,clusterrolebinding | grep "pod-admin"
kubectl describe clusterrole pod-admin
kubectl describe clusterrolebinding pod-admin
```
